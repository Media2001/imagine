## Ce qui est mesuré

- Rôles natifs `administrator`, `shop_manager`, `editor` et rôles avec une capacité accordée préfixée `manage_`, `edit_others_`, `delete_others_`, ou l'une des capacités exactes : `activate_plugins`, `edit_plugins`, `edit_themes`, `install_plugins`, `update_core`, `promote_users`, `create_users`, `delete_users`, `edit_users`, `update_plugins`, `switch_themes`, `delete_plugins`, `delete_themes`, `install_themes`, `update_themes`, `edit_theme_options`, `export`, `import`, `remove_users`. `manage_` reste volontairement inclusif, dont `manage_categories` : sur-signaler plutôt qu'omettre. Une capacité désactivée ne compte pas. `read`, `edit_posts`, `publish_posts`, `upload_files`, `delete_posts` seuls sont exclus. Seulement l'identifiant du rôle ; comptes multi-rôles dans chaque rôle et `unique_management_accounts` dédoublonné. Permissions directes isolées ou conditionnelles non reconstituées.
- Mots de passe d'application : API native `WP_Application_Passwords::get_user_application_passwords`, nombre de comptes ayant au moins une entrée ; jamais libellé, hash, date ni secret. Sur la copie portant le marqueur existant de neutralisation `imagine_staging_disabled_plugins` (même liste vide), le compte vaut **« inconnu après neutralisation »**, jamais zéro déduit des secrets effacés ; l'import et l'anonymisation restent inchangés.
- Double authentification : adaptateur **Two-Factor**, API `Two_Factor_Core::is_user_using_two_factor`. `two_factor_coverage: supported_adapter_only` borne explicitement les comptes au seul adaptateur reconnu, y compris en coexistence avec un autre fournisseur : **ce n'est pas le total certain de la 2FA du site**. API indisponible/autre extension seule : `two_factor_active: null`, adaptateur et couverture `inconnu`, **jamais zéro déduit**. Les protections d'autres extensions peuvent être présentes sans que leurs comptes soient lisibles. Le banc utilise deux extensions fictives dont une seule porte l'API, pas un audit d'un déploiement réel de Two-Factor ; aucun essai de connexion ni preuve d'une politique universelle.
- Dernière connexion : adaptateur **WP Last Login**, extension active `wp-last-login/wp-last-login.php`, métadonnée timestamp `wp-last-login`. Ancien timestamp valide : compteur `no_recent_record`. Entrée absente/nulle/invalide/future : `unknown_accounts`, sans estimer une inactivité ; aucun journal reconnu : statut `inconnu`, compteur `null`. Le cœur seul ne conserve pas un historique complet ; les sessions ne sont pas détournées en historique.
- Extensions de protection : en-têtes natifs des plugins installés, nom/version/active ou non, sans option. Familles repérées par identifiant/nom (`two-factor`, `2fa`, authenticator/login-security ; limit-login/loginizer ; wordfence/firewall/sucuri/solid/ithemes/all-in-one-wp-security). Liste de candidats identifiés, **pas une détection exhaustive ni une preuve de protection effective** ; les noms suspects sont masqués. Aucun réglage de ces extensions n'est lu ni exposé.
- Configuration : inscription et rôle par défaut natifs ; édition de fichiers d'après les booléens **du fichier original** `DISALLOW_FILE_EDIT`/`DISALLOW_FILE_MODS`, pas les valeurs forcées du confinement. Expression non littérale/doublon, définition sous condition (accolades ou syntaxe alternative), ou après un contrôle de flux dont l'exécution inconditionnelle n'est pas démontrée : inconnu ; absence = défaut natif autorisé. Analyse statique conservatrice, jamais exécution du fichier. `xmlrpc_authenticated_methods` lit le filtre natif `xmlrpc_enabled` : pas un test HTTP, ni une preuve de routage serveur ou de disponibilité des pingbacks. Disponibilité des mots de passe d'application par l'API native, sans tenter d'en utiliser un.
