## 2. Points vus par un seul, avec l'avis du fusionneur

### Vus par Codex seul — je les confirme après relecture du code

- **B1 — bloquant — le parent inscriptible peut englober le site ou le dépôt (`confine.py:61`, repris dans `Command.php:36`).** Le garde refuse un parent situé *dans* le site/dépôt, mais pas l'inverse : un parent **ancêtre** du site passe. Vérifié ligne à ligne :
  - `confine.py:61` : `parent == site or site in parent.parents or parent == repository or repository in parent.parents`. Les deux tests `… in parent.parents` n'attrapent que le cas « parent sous site/dépôt ». Le sens inverse (`site in parent`… c.-à-d. `parent in site.parents`) n'est **pas** testé.
  - `Command.php:9-11` + `:36` : `inside($path,$root)` = `$path===$root || str_starts_with($path.'/', $root.'/')`, appelé `inside($parent,$site)`. Même asymétrie, même sens de comparaison.

  Conséquence : avec un site `/travail/site` et une sortie `/travail/contenus`, le parent `/travail` est accepté ; la contrainte d'audit (`dirname(dirname($audit)) === $parent`, `Command.php:47`) est satisfaite par `/travail/audit/audit.json`. `confine(parent)` accorde alors à Landlock un droit de mutation sur tout le sous-arbre `/travail`, **y compris `/travail/site`**. Le code tiers chargé au bootstrap peut créer ou tronquer des fichiers du site malgré la garantie de lecture seule. Pire : **`--output=/x`** donne `parent = /` (aucun parent, aucune intersection détectée) → `confine('/')` ouvre l'écriture sur tout le système de fichiers.

  **Avis : réel et bloquant. Je l'avais manqué.** Mon §4 « Lecture seule prouvée » généralisait depuis les reçus `before==after` et `readonly-probe`, qui utilisaient une disposition de sortie saine ; je n'ai pas audité la logique de la garde elle-même. La garde est précisément le filet censé rendre la lecture seule *prouvée* indépendamment du chemin choisi ; son angle mort unidirectionnel + l'évasion par `/` vide cette preuve. Codex avait raison contre moi.

- **I1 — important — agrégations erronées pour les taxonomies hors domaine `posts` (`Inventory.php:251-266`).** La liste des taxonomies inclut tout `taxonomy` présent dans `term_taxonomy` plus le registre natif — donc `link_category`, enregistrée par le cœur WordPress (objets de type `link`, table `wp_links`). Or `shape()` joint `term_relationships r ON r.object_id = p.ID` **directement sur `posts`** (`:253`), et `top_terms` fait de même en `LEFT JOIN` (`:262`). `term_relationships.object_id` est générique : pour `link_category` c'est un identifiant de lien, pas de contenu.
  - Collision d'ID (un lien 41 catégorisé + un article 41) → l'état et la date de l'article sont attribués à la taxonomie de liens. Les auto-incréments `wp_links`/`wp_posts` étant indépendants, les petits ID se chevauchent facilement.
  - Sans article homonyme → la relation du lien est muette (INNER JOIN la supprime), l'objet disparaît des comptes.

  **Avis : réel. Je l'avais manqué.** Le lot promet « sans interprétation / jamais inventé » ; ici il **invente** un état de publication pour un lien, ou perd l'objet en silence. La convention `conventions`/`limitations` affirme « les comptes editoriaux restent dans posts/postmeta » sans dire que les taxonomies hors `posts` sont, elles, mal comptées. Important, parce que l'outil publie une donnée fausse sans la signaler ; l'impact réel dépend de l'usage du blogroll sur le staging, mais `link_category` est toujours enregistrée par le cœur.

### Vus par moi (Claude) seul — Codex ne les a pas relevés

Les pluriels suffixés (`related_products`) ne sont pas captés. **Avis : écart de formulation, pas de comportement.** Garder le comportement conservateur, corriger le texte.
