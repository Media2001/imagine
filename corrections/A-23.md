## 2. Points vus par un seul relecteur, avis du fusionneur

- **P1 (Codex, Important) — l'exclusion de l'administration n'applique pas
  entièrement la règle inclusive A-17 annoncée.** `Inventory.php:68-69`.
  **Confirmé après lecture du code.** A-23 juge la gestion sur `$user->allcaps`
  (capacités effectives fusionnées). A-17 juge sur la **définition du rôle**
  (`$definition['capabilities']`, `a17/Inventory.php:64,71`) et l'appartenance
  `array_intersect($user->roles, …)` (`a17/Inventory.php:84`) ; il ne dépend pas
  des capacités effectives. Or le README A-23 se lie explicitement à cette règle :
  « sans capacité de gestion reconnue par la règle inclusive A-17 … Un compte ayant
  plusieurs rôles est exclu dès qu'un est de gestion » (`README.md:51-53`).
  Divergence concrète : une surcharge individuelle négative (`edit_users=false`)
  posée sur le titulaire d'un rôle de gestion-par-définition retire la capacité de
  `allcaps` ; A-23 le classe alors **lecteur**, A-17 le classerait **gestion**.
  Dans le cas courant `allcaps` contient déjà les capacités du rôle, donc la faille
  est étroite (elle exige une surcharge négative explicite), mais réelle et contraire
  au contrat affiché. Conséquence : des comptes de gestion peuvent entrer dans les
  totaux lecteurs, les vivants et les sans-historique ; avec cinq comptes de ce type,
  une famille d'empreinte peut franchir indûment le seuil de publication. **Retenu,
  Important.**

- **i-1 (Claude, mineur) — collisions comparées à tous les comptes, administration
  comprise.** `Analysis.php:30-36`, `README.md:75-76`. Codex l'a noté comme
  interprétation explicite des notes, sans objection. Choix défendable pour la
  reprise et testé. **Avis : garder.** Question posée à Ced car elle touche les
  nombres rendus sur de vrais comptes (voir §Pour Imagine).

- **t-1 (Claude, mineur) — neutralisation détectée par simple présence de l'option
  `imagine_staging_disabled_plugins`.** `Inventory.php:36-37`. Choix conservateur
  (« inconnu » plutôt qu'un zéro faux). **Avis : garder**, dépendance à surveiller si
  l'outil d'import change cette marque (voir §Décisions techniques).

  annoncée. La vérification de Claude (`readers = 32`) est juste, mais le banc

  négative** ; il n'exerce donc jamais le cas trouvé par Codex. Le « Conforme » de
  Claude reposait sur un banc aveugle à la faille. Verdict fusionné : **À corriger.**

- **Tests.** Pas un vrai désaccord, mais deux observations distinctes à consigner.
  Claude a rejoué la **suite PHP** dans le conteneur autorisé : 1126 tests, 0 échec
  (a23 : 34 contrôles, exit 0). Claude n'a pas lancé la matrice Python (hors commande
  autorisée). Codex a tenté la suite Python en natif : `verify.py` passe (67
  contrôles, deux encodages), mais `unittest` renvoie code 1 par `PermissionError`
  (WinError 5) sur les dossiers temporaires, et la matrice Docker/WSL a échoué avant
  PHP (`Wsl/Service/E_ACCESSDENIED`). **Lecture du fusionneur :** échecs d'environnement
  local, non un échec fonctionnel du lot. Mais le fait demeure : **aucun des deux
  relecteurs n'a ré-exécuté en vert, de façon indépendante, la matrice Python complète**ni la matrice Docker ; les reçus Python ne proviennent que du paquet livré par
  Hermès. À garder en tête (un verdict n'est pas un GO).

## 4. Instructions pour Hermès (numérotées)

1. **Corriger P1.** Dans `wp/outils/bascule/a23/Inventory.php:68-69`, aligner

   appliquer le même refus fermé plutôt que d'ignorer silencieusement un tel rôle.

   deux cas : (a) un titulaire d'un rôle de gestion-par-définition avec surcharge

   plusieurs rôles dont un seul est de gestion — attendu : exclu. Ajouter les
   assertions natives correspondantes (totaux lecteurs/vivants inchangés, aucune

4. **Ne rien changer d'autre.** i-1 et t-1 restent au défaut proposé (garder) ;
