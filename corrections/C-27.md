## 2. Points vus par un seul relecteur

### Vus par Codex seul — je confirme les trois après relecture

**I1 — Important — `Acquisition.php:123` : une lecture défaillante de la source peut écraser une source existante.**
Sous le verrou, le cache `user_meta` est vidé (lignes 107-109) puis `get_user_meta($actor, SOURCE, true) === ''` décide d'écrire. Or `get_user_meta` renvoie `''` aussi bien pour une absence réelle que pour un **échec de lecture SQL** : WordPress met alors un ensemble vide en cache et renvoie `''`. Une panne transitoire à cet instant est donc prise pour « pas de source » → `update_user_meta` écrase la source déjà présente. La vérification de la ligne 125 ne protège pas : elle relit ce qui vient d'être écrit, pas la valeur antérieure. Cela contredit la règle explicite du brief : la source est alimentée **« seulement si le compte n'en a pas déjà une »**. Déclencheur étroit (erreur de lecture au bon moment), mais silencieux et indétectable. **Confirmé, Important.**

**I2 — Important — `AcquisitionConfidentialite.php:161` : l'effacement peut s'annoncer terminé en conservant la source.**
Même confusion absence / échec de lecture, en pire car le chemin est l'effacement C21. Si `get_user_meta($owner, SOURCE, true)` échoue à la ligne 161, il renvoie `''` → `delete_user_meta` n'est **pas** appelé ; la vérification de la ligne 165 relit le même cache empoisonné et passe ; la relecture des lignes 168-170 ne porte que sur les options `REPONSE`/`VUE`, jamais sur la meta `SOURCE`. Résultat : `done=true`, `items_retained=false` alors que la source personnelle reste en base — un effacement RGPD annoncé complet mais incomplet. S'ajoute l'entrelacement concurrent décrit par Codex (plus dépendant du cache persistant). **Asymétrie décisive** : `repondre()` invalide le cache `user_meta` sous le verrou (ligne 109) précisément pour éviter cela ; `effacer()` ne le fait pas avant de lire la ligne 161. **Confirmé, Important.**

**M1 — Mineur — `Acquisition.php:111` : la protection anti-redépôt ne couvre pas les propositions effacées sans réponse.**
`repondre()` ne contrôle que l'option `REPONSE` (ligne 111), jamais le tombstone posé dans l'option `VUE`. Une commande seulement *vue* (jamais répondue) puis effacée par C21 n'a pas d'option `REPONSE` → le garde-fou laisse passer. Un ancien formulaire au nonce encore valide, sur une commande toujours éligible, peut alors créer une réponse **et** une source **après** l'effacement, recréant une donnée personnelle. La promesse du README (« le marqueur interdit un redépôt ») est fausse pour ce cas. **Confirmé.** Sévérité : Codex dit Mineur ; je la garde Mineur (fenêtre étroite : nonce valide ~24 h + commande éligible + post-effacement), mais je signale l'angle RGPD — c'est une recréation de donnée effacée, à corriger sans attendre.

> Rappel doctrine (CLAUDE.md §« Règles de conduite ») : sur M1, Claude s'est trompé contre Codex. Le rapport `claude.md` écrivait que l'effacement « laisse `commande`/`etat=effacee` pour interdire un redépôt » — en supposant une protection que `repondre()` n'applique jamais. I1 et I2 n'avaient pas été vus du tout.

### Vus par Claude seul — je les retiens comme mineurs, choix prudents assumés

- **Claude-m1 — `AcquisitionConfidentialite.php:29-33`** : sur `delete_user`, boucle `do/while` + `wp_die` si le nettoyage échoue → une erreur de lecture transitoire bloque la suppression du compte. Prudent pour la donnée personnelle, mais **interagit avec I2** : si I2 renvoie à tort `items_retained=false`, cette garde ne se déclenche pas et laisse passer un compte dont la source subsiste. À corriger via I2, pas séparément.
- **Claude-m2 — `AcquisitionConfidentialite.php:45-67`** : `lignes()` renvoie `WP_Error` au moindre enregistrement malformé (jamais de faux zéro). Choix prudent, valide, à connaître.
- **Claude-m3 — `Acquisition.php:52-55`** : écriture `add_option(VUE…)` sur requête GET (effet de bord nécessaire à « une seule proposition »), `nocache_headers()` posé. Acceptable ; vigilance si un cache de page agressif est ajouté.
- **Décision technique (forme de `imagine_source_acquisition`)** : la meta reçoit l'enregistrement structuré complet, pas le seul libellé. Je la classe en décision technique (ci-dessous), pas pour Ced. À noter : I1 et I2 portent sur cette même meta.

## 4. Instructions pour Hermès (numérotées)

1. **I1 — `Acquisition.php:123`.** Sous le verrou, distinguer explicitement **absence** et **échec de lecture** de `SOURCE` avant toute initialisation : ne jamais écrire la source si la lecture est incertaine (vérifier `$wpdb->last_error` / forcer une lecture fraîche fiable), et annuler la transaction en cas d'échec. Ne pas se fier à `=== ''`.
2. **I2 — `AcquisitionConfidentialite.php:161`.** Avant de lire `SOURCE` sous le verrou, invalider le cache `user_meta` du propriétaire **comme le fait `repondre()`** (symétrie), distinguer erreur et absence, et **vérifier effectivement la suppression** avant de valider `done`. La relecture finale (168-170) doit aussi confirmer l'absence de la meta `SOURCE`, pas seulement des options.
3. **M1 — `Acquisition.php:111`.** Refuser aussi, sous le même verrou, une commande dont l'option `VUE` porte `etat=effacee` (proposition effacée) : consulter le tombstone `VUE`, pas seulement `REPONSE`. Corriger la phrase du README qui promet que le marqueur interdit tout redépôt.
4. **Tests (couvre I1, I2, M1).** Ajouter trois cas : (a) seule la première lecture de `SOURCE` échoue puis les écritures fonctionnent → source antérieure intacte, nouvelle déclaration non validée ; (b) effacement avec lecture de `SOURCE` défaillante et/ou entrelacement avec `repondre()` → `done=false`/`items_retained=true` tant que la source subsiste ; (c) POST d'un ancien formulaire après effacement d'une **proposition sans réponse** → refusé.
5. **Rejeu.** Documenter dans `A-VOIR.md` quels lanceurs n'ont pu être rejoués en relecture (recettes mutantes Python des deux côtés ; PHPUnit côté Codex). Sans incidence sur le code, mais la preuve mutante reste à exhiber côté livraison.
