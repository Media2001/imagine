## 1. Points retenus par les deux relecteurs

- **Gardien unique en place.** `wp/outils/bascule/stream_guard.py` est l'unique lecteur des deux flux (`supervise`). A20/A21 l'appellent, A12/A14/A15–A19 passent par `inventory`, A03/A11 via le pont. Les deux rapports le confirment.
- **Périmètre d'exclusion fondé.** A02 (`audit`) et A10 (`inventorier-codes`) ne bootstrappent pas le WordPress du site ; A13 est un lecteur CSV hors ligne. Leur exclusion du gardien est justifiée. Vu par les deux.
- **Commandes documentées figées** et contrôlées par un test qui passe (`documented.json`, `test_documented_commands_are_exact_source_lines`). Vu par les deux.
- **Flux refusés correctement** pour l'arrêt précoce (code 0 sans message exact) et la sortie tardive sur les flux : le gardien attend les deux EOF + la terminaison, puis statue. Déroulé à la main par les deux, cohérent avec le code.
- **Aucun octet brut réémis** : refus reconstruits depuis une liste fermée (`closed_refusal`, `stream_guard.py:72`), pas de préfixe ni de regex sur du texte du site. Vu par les deux.
- **§2.5 / §4.4 n'introduisent aucune règle métier nouvelle** ici : rattachement analogique (la promesse « rien du site ne sort »), pas une règle comptable directe. Claude (interprétation 1) et Codex (§1) concordent.
- **Limite partagée — le paquet natif A-22 n'a été validé par personne.** La matrice Python/Docker (`wp/tests/a22/matrix.py`) demande Docker/WSL et Python 3.14 Windows. Claude ne l'a pas rejouée (hors commande autorisée) ; Codex a essayé mais a buté sur `Wsl/Service/E_ACCESSDENIED` et sur des `PermissionError` dans les dossiers temporaires. **Le reçu producteur (159/159, code 0) n'est donc pas une validation indépendante** — point important pour la suite, aggravé par le P2 ci-dessous.

## 2. Points vus par un seul, avec l'avis du fusionneur

### P1 — A12 : code de refus modifié (Codex seul). **Retenu — Important.**
`stream_guard.py:138` : `re.fullmatch(r'[A-Za-z0-9_-]+', output.name)` échoue pour un nom contenant un point (`--output=.../invalid.name`) et lève `tool+'_OUTPUT_UNSAFE'`. Le dictionnaire de compatibilité `legacy_path` (ligne 129) ne couvre qu'A03 et A11 ; pour A12 il vaut `None`, donc le refus est `A12_OUTPUT_UNSAFE`. Or la validation PHP conservée `a12/Command.php:36` renvoie `A12_PATH_INVALID` pour ce même nom, et la garde Python intercepte **avant** le lancement PHP (ligne 138 précède l'appel à `supervise`, ligne 157). Le code visible par l'opérateur a donc changé.
**Avis.** Confirmé par relecture. Le brief est explicite : « Sa commande du mode d'emploi ne change pas, ses arguments non plus, **ses codes de refus non plus** ». C'est une violation littérale, pas un simple détail de diagnostic. Ni l'un ni l'autre refus ne laisse fuir d'octet (tous deux fermés), donc ce n'est pas un bloquant de sécurité — mais c'est un manquement direct à une contrainte explicite du brief. **Important.**

### A14 : codes de refus → liste fermée (Claude seul). **Retenu — même famille que P1.**
Claude (interprétation 2) note qu'A14 retombe désormais sur la liste fermée commune (repli `A14_FAILED`) au lieu de ses anciens codes. Codex a vu le même phénomène sur A12 mais pas sur A14 ; Claude l'inverse.
**Avis.** C'est **la même cause** (le gardien commun impose sa liste fermée). Nuance utile : pour A14, le brief invitait explicitement à corriger ses défauts (« partagé au besoin »), donc le changement de *comportement* est semi-sanctionné ; mais le changement de *code de refus* ne l'est pas plus que pour A12. À traiter d'un seul tenant (instruction 2).

### P2 — Empreintes A03 incomplètes (Codex seul). **Retenu — Important.**
`matrix.py:26` : `['wp/outils/bascule/a'+str(x) for x in [3,10,11,...]]` produit `a3` pour x=3. J'ai vérifié le disque : le dossier réel est `wp/outils/bascule/a03/` et contient `Policy.php`, `Report.php`, `Site.php` ; aucun dossier `a3` n'existe. `sources()` énumère donc silencieusement un dossier absent (`rglob` vide) et **n'empreinte pas ces trois sources métier d'A03**. Seul x=3 est à un chiffre dans la liste ; les autres (10–19) sont corrects.
**Avis.** Confirmé. Conséquence : le contrôle de stabilité (`sources_stable`) et l'inventaire des sources exécutées sont aveugles à toute modification de `a03/Policy.php`, `Report.php`, `Site.php`. **Cela affaiblit précisément le reçu sur lequel les deux relecteurs se sont appuyés** (voir §1, limite partagée) : la preuve est incomplète là où A03 est concerné. **Important.**

### P3 — Contenu des rapports modifiable avant publication (Codex seul). **Retenu — Important, le plus grave.**
`complete()` (`stream_guard.py:118-125`) vérifie les noms, les tailles, l'absence de lien symbolique et, pour les `.json` seulement, la syntaxe JSON. Les fichiers `.md` et `.csv` ne subissent **aucun contrôle de contenu**. Vecteur : une extension du site (chargée en processus, c'est tout le propos du lot) enregistre une fonction de fin de processus qui, après l'écriture normale du rapport par PHP, ajoute un chemin ou un nom confidentiel à `contenus.md` dans le dossier temporaire. Le sous-processus conserve le droit d'écrire dans ce dossier (Landlock autorise l'écriture sur `write_root`, `a12/confine.py:38-42` ; `disable_functions` ne bloque pas `fopen`/`fwrite`). Code 0, stdout = succès, stderr vide, `complete()` passe (fichier `.md` de bonne taille) → le parent publie le fichier altéré (`inventory` ligne 162).
**Avis.** Confirmé par lecture du code. Les quatre canaris du brief visent tous les **flux** (écriture stdout, écriture stderr, echo+arrêt, fonction de fin qui *imprime*). Aucun n'écrit dans un **fichier** de rapport. La clause « absent de tous les fichiers produits » est donc satisfaite à vide : pour les canaris de flux, aucun fichier n'est jamais publié. Ce vecteur touche la promesse centrale du lot (« aucun chemin ni aucun nom tiré du site ne sort »). Il n'est **pas** démontré de bout en bout (banc natif inaccessible aux deux relecteurs), mais la lecture du code est solide et les validateurs propres d'A20/A21 sont, eux, plus stricts. **Important** ; à surveiller comme candidat bloquant si l'exploitation est confirmée sur le banc.

### Mineurs retenus (Claude seul, non contredits par Codex).

- **Diagnostic A20.** `a20/confine.py:69` mappe le délai dépassé sur `A20_PROCESS_OUTPUT_INVALID` (pas de code de délai dédié). Refus fermé sans fuite ; seule la granularité est perdue.

## 4. Instructions pour Hermès (numérotées)

1. **A12 — rétablir le code historique.** Préserver `A12_PATH_INVALID` pour le refus d'un nom de sortie invalide. Étendre `legacy_path` (`stream_guard.py:129`) au-delà d'A03/A11, ou rétablir le code par outil. Ajouter un test de compatibilité : nom avec point → `A12_PATH_INVALID`, sans que le nom temporaire masque le nom final.
2. **A14–A19 — vérifier chaque code de refus « nom invalide ».** Tous passent par `inventory` et retombent sur `_OUTPUT_UNSAFE`. Pour chacun, confirmer le code historique documenté et le préserver. Traiter dans le même mouvement le repli `A14_FAILED` relevé par Claude.
3. **Empreintes A03 — corriger la faute de frappe.** `matrix.py:26` : `'a'+str(3)` → chemin `a03`. Refuser toute racine attendue inexistante (ne pas énumérer en silence un dossier absent). Tester explicitement la couverture de `a03/Policy.php`, `Report.php`, `Site.php`. Ajouter une mutation d'une de ces sources sur copie jetable qui exige le refus du vérificateur. Régénérer les preuves concernées.
4. **Validation du contenu final des rapports non-JSON.** Contrôler le contenu des rapports `.md`/`.csv` avant publication, avec des contrats propres à chaque outil (format et comptes autorisés), comme le font déjà A20/A21. Défaut prudent : refuser toute publication dont le contenu final n'a pas été validé.
5. **Cinquième canari — contamination d'un fichier.** Ajouter au banc une fonction de fin de processus qui contamine silencieusement un fichier de rapport (ex. `contenus.md`) sans écrire sur les flux. Exiger le refus **et** l'absence du canari dans tous les fichiers publiés. Ne pas considérer le succès des canaris stdout/stderr comme preuve de cette propriété.
6. **Revalider le paquet natif.** Après corrections, rejouer la matrice **et** le banc natif A-22 dans un environnement autorisant Docker/WSL. Ni Claude ni Codex n'a pu le valider ; le reçu 159/159 ne vaut pas validation, d'autant que P2 le rend aveugle aux sources d'A03.
