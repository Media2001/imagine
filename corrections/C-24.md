# Fusion C-24 — Formulaire de personnalisation

Fusion des deux relectures indépendantes : `relectures/C-24/claude.md` (verdict **Conforme**) et `relectures/C-24/codex.md` (verdict **À corriger**). Brief : `briefs/C-24-formulaire-de-personnalisation.md`. Cahier des charges : §3.7, §3.10, §4.2, §4.4. Divergences tranchées en relisant le code.

**Verdict fusionné : À corriger.** Je suis Codex contre moi-même. Mon rapport « Conforme » a manqué deux défauts réels, tous deux confirmés par relecture du code (R1 et R2 ci-dessous). Un « À corriger » reste le bon verdict dès qu'un point important tient.

Ce verdict n'est pas un GO (doctrine §6).

## 1. Points retenus par les deux relecteurs

- **Périmètre conforme, rien ne part.** Questions = donnée administrable en C-10 ; rubrique facultative dans Mon compte ; consentement distinct, case séparée non cochée ; compte sans email traité (rubrique présente, pas de case, consentement refusé serveur) ; réserves d'identifiants (leçon C-22) ; export/effacement natifs branchés sur C-21 ; accroches nommées (`ACCROCHE`, `APRES_INSCRIPTION_ACHAT`) sans écouteur ni transport. Aucun client Brevo, aucun `wp_mail`, aucune requête HTTP. Les deux relecteurs concordent.
- **Sécurité de base saine.** Contrôle du compte courant, POST, nonce, concurrence optimiste (`version()` + `hash_equals`), verrou MySQL, sorties échappées, requêtes préparées. Les deux concordent.
- **README manquant (mineur).** `wp/plugins/imagine-site/README.md` ne documente pas C-24 (Claude §5 ; Codex R4). Doctrine §5 : chaque extension sur mesure a un README. Retenu.
- **Localité en choix fermés = question métier.** Les deux la classent en « Pour Imagine », défaut prudent : liste fermée. Retenu, voir §5 ci-dessous.

## 2. Points vus par un seul, avec l'avis du fusionneur

### Vus par Codex seul — retenus, importants

- **R1 — Important — `PersonnalisationReglages.php:144` : la restauration après échec du journal est cassée.** Codex a raison, et j'avais manqué le défaut : je n'avais noté que « chemin de rollback non testé » (mineur), sans voir qu'il est **faux**. Mécanique vérifiée : `nettoyer()` est le `sanitize_callback` enregistré (lignes 15-16). Au retrait d'une question, si `add_option($name, $event)` échoue (ligne 140), la branche de restauration appelle `update_option($key, $old, false)` (ligne 144), ce qui **réexécute `nettoyer($old)`**. Or le drapeau `$restoring` ne court-circuite que `journal()` (ligne 132), jamais `nettoyer()`. Pendant la restauration, `$current` est déjà le nouveau catalogue (l'option a été écrite avant le hook `updated_option`) : la question retirée est absente de `$current` mais sa réserve existe → lignes 80-81 lèvent « Question réservée » → `nettoyer` renvoie le catalogue courant (le nouveau) → `update_option` n'écrit rien → ligne 145 `get_option !== $old` → `wp_die(500)`. Résultat : réponse 500, nouveau catalogue conservé **sans** entrée de journal, au lieu du retour à l'ancien état. Même chemin au retrait d'un choix. **Avis du fusionneur : retenu, important.** Défaut de correctitude réel, dans un chemin non couvert par les tests.

- **R2 — Important — `Personnalisation.php:52` : une inscription newsletter créée par défaut vaut « inscrit » pour la transmission.** Codex a raison, et je l'avais manqué : j'avais validé la conjonction sans regarder l'origine de la préférence. `attributsConnecteur` pose `$newsletter` à vrai dès qu'une préférence a `['choix'] === true`, **sans regarder `origine`**. Or `Newsletters::creation` (ligne 91) fabrique exactement cette valeur avec `origine = 'defaut_creation'` quand le réglage de création C-22 est actif ; le code lui-même marque cette origine « pas un consentement explicite » (`Newsletters.php:95` et l'affichage ligne 166-167). `transmissible` (`PersonnalisationRegles.php:63`) ne teste que le booléen. Donc un compte avec email, réponses et consentement de personnalisation devient transmissible alors que le lecteur n'a jamais accepté lui-même de newsletter : l'accroche `ACCROCHE` (`Personnalisation.php:93-94`) émettrait ses attributs vers un futur connecteur. Cela confond les deux consentements distincts exigés par §3.10 et §4.4, et une case pré-cochée n'est pas un consentement valable (RGPD). Aucun envoi n'existe aujourd'hui, mais le contrat livré est trop permissif. **Avis du fusionneur : retenu, important.** Nuance : le risque n'est réalisé que si le réglage « inscription par défaut à la création » de C-22 (`imagine_newsletters_creation = oui`) est actif ; même dormant, la porte doit être resserrée. La part « que veut dire *inscrit à au moins une newsletter* » est aussi une question métier (voir §5).

### Vus par Codex seul — retenu, mineur

- **R3 — Mineur — `PersonnalisationReglages.php:25` : plusieurs instructions par ligne, contraire à PSR-12 (doctrine §5).** Factuellement exact : la classe comprime des instructions (ex. lignes 23, 25, 157, 181). Mon rapport affirmait « Conventions §5 respectées » : c'était trop rapide sur ce point. **Avis du fusionneur : retenu mais faible priorité.** Le style dense est répandu dans tout le dépôt (ce n'est pas propre à C-24) ; à traiter comme réglage de style global, pas comme blocage de ce lot. Voir « Décisions techniques ».

### Vus par Claude seul — retenus, mineurs

- **Injection HTML dans C-10 non couverte par un test d'intégration.** Le wrapper `admin_menu` priorité 145 (`ob_start` / `strpos '</form>'` / `substr_replace`, conditionné par `value="imagine_reglages"`, lignes 18-34) n'est testé qu'indirectement (capture Chromium). Si le markup C-10 change, la section disparaît **en silence**. État actuel sain (ordre des priorités sûr), risque = régression future de markup. Codex ne l'a pas relevé. **Retenu, mineur.**
- **Compteurs de tests périmés dans la doc.** `A-VOIR.md`/`TRANSMISSION.md` annoncent « 1 126 tests / 35 550 assertions » ; mon rejeu local donne **1 128 / 35 565**. Écart bénin, à rafraîchir. **Retenu, mineur.**

## 4. Instructions pour Hermès

1. **Réparer la restauration de `journal()` (R1).** Séparer la **restauration interne d'une préimage déjà vérifiée** de la validation d'une nouvelle saisie : pendant la restauration, ne pas repasser `$old` par le validateur qui refuse les identifiants réservés (le drapeau `$restoring` doit protéger la restauration, pas seulement `journal()`), puis **relire l'état restauré** pour confirmer. Ajouter deux tests injectant l'échec du journal après le retrait d'une question **et** après le retrait d'un choix : vérifier le retour effectif à `$old` (pas seulement le code HTTP) et l'absence de 500.
2. **Resserrer la porte « inscrit à au moins une newsletter » (R2).** Dans `attributsConnecteur`, ne compter une préférence newsletter que si son origine est un **accord explicite du lecteur** (origine `lecteur`) ; exclure `defaut_creation` et toute origine inconnue. Ajouter des tests : une préférence `defaut_creation` ferme la projection ; un accord newsletter explicite l'ouvre, toutes autres conditions réunies.
3. **Compléter `wp/plugins/imagine-site/README.md`** (R4 / Claude §5) : rôle des quatre classes, réglage C-10, deux métadonnées, accroches, et commandes de test `c24-*` en distinguant le contrôle local des parcours nécessitant le site de démonstration.
