## 1. Points retenus par les deux relecteurs

- **Conformité de fond.** Page « Bienvenue » native, texte laissé vide, lien vers l'entrée abonnement ; trois codes fictifs ; liste fermée journalisée (Settings API + `manage_options` + journal C10) ; session WooCommerce native, candidat au checkout, scellé immuable au paiement sous verrou SQL ; compteurs par code distincts de C-27, sans identité ; callbacks de confidentialité C-21. Le code ne touche **ni prix, ni coupon, ni source d'acquisition du compte** ; aucun traceur, aucun appel sortant ; commande C-16 (`created_via=imagine-c16`) exclue ; rien vers Odoo ni newsletter. Conforme au brief.
- **Exactitude métier.** Les deux déroulés concordent : dernier code **valide** connu avant la commande (un inconnu n'écrase pas) ; candidat provisoire revalidé au checkout ; transfert scellé idempotent (verrou `GET_LOCK` + sceau) ; bornes de période UTC incluses ; date impossible refusée (parse strict `!Y-m-d`). Aucun écart de résultat.
- **Preuve `prix_identique` faible.** Vue par Claude (mineur 4) **et** Codex (I2). Divergence de gravité, tranchée en 3.
- **Doctrine « standard d'abord ».** Attribution native Sourcebuster documentée et volontairement non réutilisée pour un code imprimé ; session = `WC_Session_Handler` natif, pas de cookie maison ; sources officielles conservées dans `production/C-30/standard2-V2.json`. Conforme.
- **Suite scellée partielle.** Les deux constatent que la couche WooCommerce n'est exercée en déterministe que par la mutation du contrôle d'appartenance ; le reste tient par les scripts vivants / preuves archivées. Claude en fait un point important structurel (I-C) ; Codex en tire deux instances concrètes (I1, I2). Les deux lectures se renforcent.

## 2. Points vus par un seul relecteur — avis du fusionneur

### Retenus (vus par Codex seul, confirmés par relecture du code)

- **I1 — important — `CodesSuivisConfidentialite.php:28` : commandes invitées omises de l'export et de l'effacement. CONFIRMÉ.**
  `commandes()` fixe `customer_id` à l'ID du compte dès qu'un compte existe pour l'adresse, et **n'ajoute `billing_email` que si le compte n'existe pas** (ligne 30 : `if (!$user) { $args['billing_email'] = $email; }`). Donc, compte existant, une commande invitée (`customer_id=0`) portant cette adresse et un code suivi n'est jamais lue. Enchaînement concret : un client qui possède déjà un compte achète déconnecté, ou une ancienne commande invitée n'est pas rattachée après création du compte. Conséquence : `exporter()` l'ignore, et `effacer()` renvoie `done=true` / `items_removed` sans positionner `items_retained` — l'effaceur **affirme avoir fini alors que le code et son libellé subsistent** sur la commande invitée. Le brief impose pourtant « Donnée rattachée à une commande : déclarée à l'export et à l'effacement de C-21 » : une commande invitée avec code **est** une donnée rattachée à une commande. **Claude avait classé ce chemin « Conforme » ; révisé en défaut important.** Non couvert par les tests : la fixture de confidentialité n'utilise que des commandes rattachées au compte.

- **M1 — mineur — `CodesSuivisAdmin.php:79` et `CodesSuivisRegles.php:16` : l'aide de saisie contredit le validateur. CONFIRMÉ.**
  L'aide annonce « code de 1 à 40 caractères minuscules, chiffres ou tirets », mais le validateur impose `^[a-z][a-z0-9-]{0,39}$` — **une lettre minuscule en première position**. Un code comme `2026-affiche` respecte l'aide et est pourtant refusé, avec le seul message générique « Liste invalide ». Écart cosmétique et de documentation, aucun risque de sécurité. Retenu, faible enjeu.

### Retenus (vus par Claude seul, confirmés par relecture du code)

- **I-C — important — couche WooCommerce sans test scellé rejouable.** Toute la logique branchée sur Woo (`retenir`, `candidat`, `payer` : scellé/verrou/immuabilité, `compter`, export, effacement) n'a aucun test déterministe dans la suite scellée ; seul `CodesSuivisRegles` (pur) est couvert, plus une mutation témoin. C'est précisément cette asymétrie qui a laissé passer I1 (bug de données) et I2 (preuve tautologique). Les lots voisins ont un test d'adaptateur scellé sur bouchons Woo (ex. `AcquisitionAdapterTest` pour C-27). Doctrine §4 « les tests d'abord », grille §3. Retenu, important.
- **I-B — important — `CodesSuivis.php:54` et `:85` : périmètre limité au checkout classique.** `candidat()` et `payer()` exigent tous deux `get_created_via() === 'checkout'`. Un panier passé par le checkout Blocks / Store API (`created_via=store-api`) ne reçoit jamais de code, candidat comme scellé. Limite **déclarée** par Hermès (A-VOIR.md), donc recevable au sens de la doctrine §1, mais à trancher avant que le thème ne fige son tunnel. Voir Décisions techniques.
- **Mineur — `CodesSuivis.php:123` : `compter()` charge toutes les commandes payées et filtre les dates en PHP**, sans borne `date_paid` en requête → coût en O(toutes les commandes payées). Acceptable à l'échelle d'Imagine, à surveiller.
- **Mineur — `CodesSuivis.php:129` : `compter()` compte par code stocké** (`instantane()`, validation structurelle), pas par appartenance à la liste **actuelle** : un code retiré de la liste réapparaît dans les nombres pour les commandes passées. Interprétation raisonnable (attribution historique) mais non écrite — à documenter.
- **Mineur — la page « Bienvenue » n'existe que par le seed de démonstration** (`wp/outils/demo/c30-seed.py`), pas par un script de bascule. Conforme à « démo uniquement » ; le chemin de création en production (contenu Imagine) reste à préciser.

## 3. Désaccords

- **Gravité de `prix_identique` (`wp/tests/demo/c30-runtime.php:49`).** Claude : mineur (le code ne touche jamais le total, donc faible enjeu). Codex : important (I2 : les deux totaux sont fixés à `12.34` par la même fabrique, sans produit, panier ni calcul natif ; la preuve ne détecterait pas une remise ou des frais introduits dans les hooks de calcul). **Tranché en faveur de Codex → important.** Motif : le brief nomme explicitement cette preuve dans sa section *Preuve* (« aucun prix changé — le total de la commande est celui d'un achat sans code »). La grille §3 demande qu'un test « vérifie vraiment la règle » et non qu'il « répète le code » ; ici la preuve d'une garantie imposée par le brief est quasi tautologique, donc effectivement absente. Le comportement du code reste correct (le code n'entre jamais dans le total) — c'est la **preuve** qui est en défaut, pas la fonction.

- **« Export / effacement C-21 ».** Claude : « Conforme ». Codex : défaut I1. **Tranché en faveur de Codex** (voir 2, I1). Le « Conforme » de Claude est révisé.

- **Exécution de la suite PHP.** Claude a réussi le rejeu en conteneur jetable scellé (`rejouer.ps1` → « 1219 tests, 36748 assertions, 0 échec — PASS » ; `CodesSuivisC30Test` vert ; isolation `network=none`/`rootfs=ro`/`cap-drop=ALL` confirmée). Codex n'a **pas** pu lancer PHPUnit (`php` hors PATH) ni Docker (`Wsl/Service/E_ACCESSDENIED`, 0 test exécuté) et s'est appuyé sur les preuves archivées. Ce n'est pas un désaccord de fond : la preuve d'exécution scellée de C-30 est **tenue** (côté Claude), ce qui lève la réserve finale de Codex « le rejeu PHP reste à effectuer ». À noter toutefois : la suite scellée ne couvre pas la couche Woo (I-C), donc son PASS ne vaut pas preuve des chemins I1/I2/I-B.

## 4. Instructions pour Hermès (numérotées)

1. **Couvrir les commandes invitées dans l'export ET l'effacement C-21 (I1).** Dans `CodesSuivisConfidentialite::commandes()`, sélectionner l'**union** des commandes du compte (quand il existe) et des commandes invitées portant l'adresse de facturation vérifiée, avec dédoublonnage par ID et pagination stable. L'effaceur ne doit retourner `done`/`items_removed` que si **toutes** les commandes portant un code pour cette adresse ont été traitées ; sinon positionner `items_retained`. Ajouter un test scellé réunissant une commande liée au compte, une commande invitée de même adresse et une commande d'un tiers : exporter et effacer les deux premières, préserver la troisième.
2. **Ajouter un test d'adaptateur scellé sur la couche Woo (I-C).** `CodesSuivisAdapterTest` sur bouchons Woo, couvrant session (`retenir`), candidat, scellé/verrou/immuabilité (`payer`), comptage (`compter`), export et effacement — à l'image de `AcquisitionAdapterTest` de C-27 — pour que le rejeu prouve la règle sans site vivant. Ce test est le filet qui aurait attrapé I1 et I2.
3. **Renforcer la preuve de non-modification des prix (I2).** Remplacer `prix_identique` par une comparaison de deux achats fictifs du **même produit**, mêmes quantités et mêmes conditions, avec et sans code, après **calcul WooCommerce** ; vérifier total, remises et coupons (`get_coupon_codes() === []`), puis restaurer les objets. Le test doit pouvoir **échouer** si une modification de prix liée au code est introduite dans les hooks de calcul.
4. **Aligner l'aide de saisie sur le validateur (M1).** Dans `CodesSuivisAdmin::reglages()` (ligne 79) et le README, préciser « code commençant par une **lettre minuscule**, puis minuscules, chiffres ou tirets, 1 à 40 caractères ». Couvrir l'exemple `2026-affiche` (refusé) dans le test de validation. Défaut prudent : conserver le validateur tel quel et corriger le texte.
5. **Raccorder le checkout Blocks / Store API, ou en prouver l'absence d'impact (I-B).** Voir Décisions techniques ; appliquer le défaut proposé.
6. **Documenter le comptage historique.** Écrire, dans le README et l'A-VOIR, que `compter()` compte par code **stocké sur la commande** (attribution historique), si bien qu'un code retiré de la liste reste visible dans les nombres des commandes passées. Défaut prudent : conserver ce comportement (attribution historique), le rendre explicite.
7. **Mineur, efficacité.** Si le volume de commandes payées le justifie un jour, borner `compter()` par `date_paid` dans la requête `wc_get_orders` plutôt que de filtrer les dates en PHP. Non urgent à l'échelle d'Imagine.

## Décisions techniques, défaut proposé (Hermès applique, Claude arbitre après coup)

- **Checkout Blocks / Store API (I-B).** `candidat`/`payer` ne se branchent que sur `created_via === 'checkout'`. *Défaut prudent proposé :* garder le périmètre checkout classique **et** raccorder aussi le chemin Store API (`woocommerce_store_api_checkout_order_processed`, ou accepter `created_via ∈ {checkout, store-api}`), afin que l'attribution ne dépende pas du type de tunnel retenu côté thème. À défaut d'un raccord, écrire un test qui prouve qu'un code n'est jamais perdu sur le tunnel **réellement** utilisé par le site. Hermès applique ce défaut sans attendre ; Claude arbitre après coup.
