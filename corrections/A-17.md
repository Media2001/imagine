Codex a passé `verify.py` (20 contrôles) et la comparaison d'empreintes (26 dépendances identiques). Rien de réel ni de secret dans les sorties **nominales**. (La réserve R5 ci-dessous ne porte que sur le chemin de **refus**.)
- **Borne exacte des 12 mois non exercée par une fixture.** Les deux la relèvent (moi en mineur, Codex en §2.3). Le code est correct par lecture (`$last < $cutoff` strict, `Inventory.php:98`), mais aucune fixture n'est pile à `2025-11-26T12:00:00Z`. Retenu, mineur.

Limite de preuve partagée, à garder explicite.
- **Conformité générale, doctrine « standard d'abord », PSR-12 strict.** Conformes pour les deux.

## 2. Points vus par un seul, avec l'avis du fusionneur

- **R5 (Codex, bloquant) — fuite d'un chemin porteur d'identité sur refus. CONFIRMÉ.** `a11/Runtime.php:59-61` parcourt tout l'arbre du site ; sur un lien symbolique il lève `A11_SYMLINK_UNSUPPORTED` avec `details['file']` = le chemin relatif **arbitraire**. `refusalMessage` (`Runtime.php:21`) le `json_encode` dans le message, et `inventorier-securite:37-39` le recopie **sans filtrage** sur stderr. Un lien nommé `wp-content/uploads/A17_LOGIN_PRIVATE_CANARY.pdf` sort donc le canari. Le brief est absolu : « aucun nom, aucune adresse… ne sort de l'outil ». **Avis : retenu bloquant.** Nuance que j'ajoute : le README (ligne 9) assume de **nommer** les fichiers refusés — c'est sûr pour la **liste fermée** des drop-ins (`db.php`, `object-cache.php`…, `Runtime.php:54-56`, noms techniques), mais **pas** pour le balayage des liens symboliques, dont le chemin est contrôlé par le contenu du site. Le défaut est donc borné à ce seul chemin, et le correctif est léger.

- **R1 (Codex, important) — compteur de mots de passe d'application perdu après anonymisation. CONFIRMÉ.** `staging/lib.php:346-348` supprime toute ligne dont `meta_key` matche `sensitiveKey` ; le motif (`lib.php:270`) inclut `application_passwords`. L'usermeta `_application_passwords` disparaît donc à l'import. Ensuite `WP_Application_Passwords::get_user_application_passwords()` (`Inventory.php:85`) renvoie `[]` → `application_password_accounts` vaut **0 pour tous**, y compris les comptes qui en portaient. Or le brief promet : « Sur un site anonymisé par l'import, les nombres restent justes ». Le banc masque le trou : `seed.php:13` crée le mot de passe **directement** dans la fixture, sans traverser l'import — la preuve est verte mais n'exerce pas le vrai chemin. **Avis : retenu important.** Je l'avais manqué ; Codex a raison.

- **R2 (Codex, important) — rôles de gestion omis. CONFIRMÉ.** `Inventory.php:12-13` reconnaît `create_users`, `delete_users`, `promote_users`, mais **pas `edit_users`** ; il omet aussi `update_plugins` et `switch_themes`. Un rôle sur mesure portant seulement `read` + `edit_users` renvoie `false` dans `management()` et **disparaît des agrégats**. Cela contredit « tout rôle sur mesure portant une capacité de gestion » (brief). Direction dangereuse pour un état des lieux : on **sous-compte** les comptes à examiner. **Avis : retenu important.** (Réconciliation avec mon point « manage_ » : voir §3.)

- **R3 (Codex) — total 2FA présenté comme certain malgré une couverture partielle. CONFIRMÉ, mais tempéré.** `Inventory.php:50,86,93-94` ne compte que l'adaptateur Two-Factor ; un compte protégé par un autre fournisseur actif (visible dans `protections[]`) est compté comme **sans** 2FA. **Avis : abaissé à mineur.** Deux raisons : (a) le README **le dit déjà** (« Les protections d'autres extensions peuvent être présentes sans que leurs comptes soient lisibles ») ; (b) la direction est **conservatrice** — on sous-estime la couverture, donc on sur-signale le risque, jamais l'inverse. Reste à faire : un test de coexistence et, au choix, une mention de couverture par fournisseur pour que `two_factor_active` ne se lise pas comme un total certain.

- **R4 (Codex, important) — faux diagnostic sur une `define` conditionnelle. CONFIRMÉ, mais marginal.** J'ai rejoué la tokenisation de `<?php if (false): ; define('DISALLOW_FILE_EDIT', true); endif;` : à la syntaxe alternative, `configBoolean` (`Inventory.php:149`) voit `depth === 0` et le token précédent `;`, retient donc `true` alors que la ligne n'est jamais exécutée → `admin_file_editing=false` (risque **sous-estimé**). Le README promet « inconnu » pour une expression non résolue. **Avis : abaissé à mineur.** Le défaut est réel par lecture, mais la probabilité qu'un `wp-config.php` réel utilise `if(false): … endif;` est quasi nulle (les `define` y sont en tête de fichier, au plus sous `if(!defined()){…}` en accolades — déjà traité `null` par la profondeur). Correctif cheap et sain quand même.

- **Chemin « dernière connexion = inconnu » non testé (moi, important). RETENU.** Le brief exige : « sinon « inconnu », jamais une estimation ». Ce chemin est implémenté (`Inventory.php:51,73-74,87,96-97`) mais jamais exercé : `inside.py` active toujours `wp-last-login`. Seul le « inconnu » du **2FA** est prouvé, pas celui de la **connexion**. Codex a confirmé le comportement par lecture (§2.2) mais ne l'a pas isolé comme trou de test. **Avis : retenu important** (branche requise non prouvée).

- **Portée large de `manage_` (moi). RETENU comme décision technique.** Le préfixe capte aussi des capacités de contenu (`manage_categories`…). Direction **sûre** (sur-signale). **Avis : garder le défaut inclusif**, mais cela **ne remplace pas** le correctif R2 (voir §3 et instruction 3).

- **Arithmétique au 29 février (moi). RETENU mineur.** `modify('-12 months')` bascule au 1er mars une année bissextile. Marginal. Documenter.

## 3. Désaccords

- **Contradiction apparente R2 ⇄ « manage_ » : tranchée.** Mon rapport dit l'allowlist **trop large**, Codex la dit **trop étroite**. Après relecture de `Inventory.php:12-13`, **les deux sont vrais sur deux facettes** : le préfixe `manage_` est trop inclusif (capte `manage_categories`), et la liste exacte est trop restrictive (rate `edit_users`, `update_plugins`, `switch_themes`). Pour un état des lieux de sécurité, la facette qui compte est la **sous-inclusion** (R2) : elle **masque** des comptes dangereux. Elle doit être corrigée. La sur-inclusion est la direction sûre : on la garde. Les deux relecteurs ont donc raison ; ce n'est pas un désaccord de fond mais deux moitiés du même constat.

- **Présence d'un bloquant : tranché pour Codex.** Mon rapport conclut « aucun bloquant » ; Codex lève R5. La relecture du code confirme la fuite et le brief pose une garantie **absolue** de confidentialité. Je me range à Codex : **R5 est bloquant**, borné au chemin de refus sur lien symbolique.
