## 3. Désaccord

**Verdict : Claude *Conforme* contre Codex *À corriger*. Codex a raison. Je tranche pour *À corriger*.**

Objet du désaccord : **R1 (`confine.py:30`, `inventorier-portes:16-31`).** Le bootstrap charge WordPress entier — `require ABSPATH . 'wp-settings.php'` (`a11/Runtime.php:127`) — donc les extensions actives du site exécutent du code arbitraire pendant le démarrage. Or la protection de sortie de `inventorier-portes` est incomplète :

- `ob_start()` ne capture que **stdout**, pas stderr. Une extension qui fait `fwrite(STDERR, __FILE__)` écrit un chemin directement à l'opérateur, hors tampon.
- Le `try/catch` n'intercepte **ni** `exit('CANARI')` (termine avant le nettoyage ; le tampon est vidé à l'extinction), **ni** une fonction de fin de processus (`register_shutdown_function`) qui s'exécute **après** `ob_end_clean()` et après l'annonce de succès `A21_OK`.
- `confine.py` fait `os.execvp('php', …)` sans superviser les flux. `display_errors=0`/`log_errors=0` et Landlock ne filtrent pas ces écritures explicites.

Conséquence : un chemin ou un nom tiré du site peut atteindre l'opérateur, **y compris sur le parcours nominal réussi**. Cela contredit frontalement la règle de la voie 1 inscrite au brief ligne 21 : « aucune sortie, **sortie d'erreur comprise**, ne recopie un chemin ou un nom tiré du site ». C'est l'objet même du lot (les portes vers l'extérieur, confidentialité du flux, §2.5/§4.4). Un contournement de cette garantie est **bloquant**.

**Ce que Claude a manqué.** Sa relecture affirme « Aucune fuite de nom/chemin du site, sortie d'erreur comprise » (§4). Cette affirmation est fausse : elle ne couvre que les chemins de sortie **de l'outil** (SELECT, exception rabattue sur code fermé), pas le code d'extension exécuté au `require wp-settings.php`. Le rejeu PHP de Claude est resté au vert parce que les fixtures de bootstrap ne contiennent pas d'extension hostile écrivant sur stderr, appelant `exit()`, ou imprimant en fin de processus — c'est aussi une lacune de test (voir instruction 1).

**Nature du constat.** Analyse statique du chemin d'exécution, partagée par Codex. Reproduction PHP non exécutée (banc Docker/WSL indisponible côté Codex : `Wsl/Service/E_ACCESSDENIED` ; hors commande autorisée côté Claude). La réalité du contournement tient à la lecture du code ci-dessus, pas à un rejeu.

Sur le reste, pas de désaccord : les deux relectures convergent.

## 4. Instructions pour Hermès

1. **R1 — corriger le filtrage des sorties du processus PHP confiné (bloquant).** Faire superviser le processus PHP par un lanceur qui capture **ses deux flux** (stdout + stderr) jusqu'à la terminaison, et ne restitue à l'opérateur que des messages reconstruits depuis la liste fermée d'erreurs. Refuser toute sortie inattendue **et** tout succès incomplet (y compris une sortie apparue après l'annonce `A21_OK`). Conserver le confinement du processus enfant. Ajouter des fixtures de bootstrap : extension écrivant directement sur stdout, sur stderr, appelant `exit('CANARI')` tôt, et enregistrant une fonction de fin de processus qui imprime un canari. Vérifier l'absence de canari sur **tous** les flux et dans tous les rapports, y compris après l'annonce de succès.
2. **R2 — sceller les dépendances courantes dans `verify.py` (mineur).** Comparer aussi les dépendances exécutées (A-11, A-12, A-02, neutralisation) aux fichiers courants, en conservant l'exception documentée du README partagé (`readme_contract`). Ajouter un cas de test de dérive d'une dépendance qui doit faire échouer le vérificateur.
3. **Magasin d'extensions — aligner code et README (mineur, décision technique).** Soit appeler `WC_Helper::is_site_connected()` pour coller au standard cité par le `README.md`, soit garder la lecture directe de l'option et corriger le `README.md` pour l'annoncer. Défaut proposé plus bas.
4. **Ajouter un test de webhook actif à hôte littéral IP/IPv6 (mineur).** Vérifier le classement (`unknown` ou `external_domain` selon la règle de chaîne) et l'absence de fuite.
