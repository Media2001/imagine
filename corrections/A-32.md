## 2. Points vus par un seul, avec l'avis du fusionneur

### C02 — important — codes de refus perdus (Codex seul ; Claude s'était trompé)
`wp/outils/bascule/tournee/tournee.py:51-67`. CONFIRMÉ par lecture du code.
- `allowed_messages()` (51-55) ne lit que `guard.allowed_messages()` ∪ `tournee/refusals.json`.
- `guard.allowed_messages()` (`stream_guard.py:103-110`) = `stream_refusals.json` + variantes dynamiques `A11_DROPIN_UNSUPPORTED` et `A16_MAPPING_KEY_ABSENT` seulement.
- Les codes de **supervision** que le gardien émet réellement pour les outils inclus — `A11/A12/A15/A16/A17/A18/A19 _PROCESS_OUTPUT_INVALID`, `_PROCESS_TIMEOUT`, `_SUCCESS_INCOMPLETE` (émis en `stream_guard.py:174-177`) — ne figurent **ni** dans `stream_refusals.json`, **ni** dans `refusals.json` (qui n'a aucune entrée A-15 à A-19). Le gardien lui-même doit les rajouter à la main dans `public_error()` (`stream_guard.py:113-116`) : preuve qu'ils sont hors liste statique.
- Conséquence : quand un outil inclus dépasse le délai, rend une sortie invalide ou une réussite incomplète, il écrit `code 1 / stdout vide / A15_PROCESS_TIMEOUT\n`. `classify()` ne le trouve pas dans `closed` et le range en « en échec (1) », **sans le code**. Le brief (§ « écrit un bilan ») exige le code du refus.
- Incohérence qui le prouve : `A20_PROCESS_OUTPUT_INVALID` **est** dans `refusals.json` et serait, lui, classé « refusé » avec code. Deux refus de même forme, deux traitements.
- **Claude écrivait « pas de trou… couverture des quinze outils vérifiée à la main » : c'est faux.** Il avait contrôlé les listes statiques mais manqué les codes de supervision dynamiques des outils supervisés.

### C04 — important — fausse déclaration d'environnement acceptée (Codex seul ; Claude s'était trompé)
`wp/outils/bascule/tournee/tournee.py:93-100`. CONFIRMÉ par lecture du code.
- La substitution ligne 93-94 **conserve le contenu des chaînes** (`else match[0]`) et n'efface que les commentaires.
- Donc un `wp-config.php` contenant `$note = "define('WP_ENVIRONMENT_TYPE', 'staging');";` garde ce texte. `re.findall` (95) y trouve une « déclaration », `config.count('WP_ENVIRONMENT_TYPE') == 1`, et `verified_site()` accepte un site **sans aucune constante d'environnement déclarée**.
- Cela contredit le README qui annonce refuser les déclarations absentes, et la preuve « zéro outil lancé » ne couvre pas ce cas.
- **Claude écrivait « lit wp-config.php sans exécuter PHP (purge des commentaires sans toucher aux chaînes). Bon » : il a pris le défaut pour une qualité.** Ne pas toucher aux chaînes est précisément ce qui laisse un `define` de chaîne compter comme code.
- Portée honnête : la garde reste gardée en amont par le marqueur JSON (`status=verified`, `offline_verified`, `runtime_probe_passed`, `environment=staging`). C04 ne franchit pas le marqueur ; il supprime le contre-contrôle `wp-config`. C'est une défense en profondeur qui tombe, pas un accès direct à un site de production. Important, non bloquant. Le code fautif est **propre à A-32** (réécriture Python de la lecture), donc corrigible sans toucher à A-05.
