# Fusion C-10 — L'écran de réglages

Date : 2026-11-23. Lot : `briefs/C-10-ecran-de-reglages.md`.
Fusion des deux relectures indépendantes : `relectures/C-10/claude.md` (relecteur) et `relectures/C-10/codex.md`.
Là où les rapports divergent, j'ai tranché en relisant le code (`wp/plugins/imagine-pilotage/src/Administration/Reglages.php`, les adaptateurs C-05/06/07) et le brief.

**Verdict fusionné : À corriger.** Un point bloquant (tests), trois importants, trois mineurs.

---

## 1. Points retenus par les deux relecteurs

- **Conformité d'ensemble.** Menu natif Imagine, page Réglages, trois domaines (Accès, Paiement, Liste d'envoi), huit champs, un seul formulaire Settings API vers `options.php`, réutilisation des trois adaptateurs sans toucher aux moteurs. Les deux relecteurs le confirment.
- **Sécurité.** `manage_options` sur le menu, la page et le groupe Settings API ; re-vérification de capacité avec 403 (`Reglages.php:189-191`) ; nonce par la Settings API ; validation stricte des clés et des choix ; échappement des sorties ; `$wpdb->prepare()` + `esc_like()` pour le journal ; options non exposées en REST ; aucun secret. Les deux rapports concordent : rien de bloquant côté sécurité.
- **Exactitude métier des valeurs proposées.** Marge vide → le planificateur refuse, aucun défaut inventé ; droits PDF cohérents avec le moteur ; format C07 conservé dans l'ordre et doublon refusé ; changement d'année correct. Aucune nouvelle interprétation métier non déclarée dans les valeurs. Les deux relecteurs ont déroulé ces cas à la main et concordent.
- **Accès et Paiement ne sont raccordés à aucun consommateur.** Fait établi par les deux (Claude §1.1 via `production/C-10/notes.md:45` ; Codex C10-01 via la lecture du raccord). Seul le réglage Liste d'envoi produit un effet observable, et uniquement sous forme d'aperçu CSV **dans la page d'admin**, produit par le vrai exporteur C07 (`Reglages.php:229-232`, `apercuCsv()` `:254-261`). Les deux en tirent des conséquences différentes : voir §2 (Codex : corriger le texte de l'écran) et §5 (Claude : arbitrage).

## 2. Points vus par un seul relecteur, avec avis du fusionneur

### Vus par Claude seul

**2.1 — Absence totale de tests PHPUnit pour la façade (classé bloquant par Claude).**
`Administration\Reglages` (`clesExactes()`, `nettoyerAcces()`, `nettoyerPaiement()`, `refuser()`, `journaliser()`, `ajouterAuJournal()`, `apercuCsv()`) n'a aucun test dans `composer test`. `tests/Administration/` n'existe pas ; `phpunit.xml` ne déclare pas la suite. Les comportements exigés au livrable n°1 (droits, nonce, valeurs invalides, journal) ne sont vérifiés que par des tests Python HTTP contre le site de démonstration, hors suite et non rejouables en relecture.
**Avis : retenu, et maintenu bloquant.** Vérifié : la logique de validation est du PHP pur (pas d'appel WordPress dans `clesExactes`/`refuser`/la dé-duplication du journal), donc testable avec le `WordPressFictif` déjà présent (`tests/Acces/WordPressFictif.php`), comme le font déjà les adaptateurs. Le brief liste « ses tests » au livrable n°1 ; la doctrine §4 exige une logique testable sans WordPress et §6 adosse la clôture à « tests au vert » dans `composer test`. L'écart est direct. **Codex n'a pas évalué cette absence** (il a lancé le test Python de périmètre et comparé des empreintes, sans relever le manque de suite PHPUnit pour la façade) : sur ce point précis, Claude a vu ce que Codex a manqué.

**2.2 — Cas limite Paiement : premier enregistrement invalide → persistance d'un `[]` (classé important par Claude).**
Chemin vérifié dans le code : `nettoyerPaiement()` exige d'abord les clés exactes (`Reglages.php:88`), puis délègue à `ReglagesAdministration::sanitiser()`, qui, sur exception, retourne `get_option(self::OPTION, [])` (`ReglagesAdministration.php:56`). Si l'option n'a **jamais** été enregistrée, cela retourne `[]`, alors persisté. Comme `page()` lit le Paiement par `get_option()` **brut** (`Reglages.php:193`), pas par `->lire()`, l'écran afficherait ensuite des sélecteurs vides au lieu des défauts prudents.
**Avis : retenu, réel mais à nuancer en impact.** Reachability étroite (il faut que la toute première écriture de l'option porte des clés exactes et une valeur de type invalide ; le test Python enregistre toujours les défauts d'abord — `c10-verifier.py:145` — donc ne couvre pas ce cas). Impact display-only : les consommateurs restent saufs car ils passent par `depuisOption([])` qui recompose les défauts ; aucune ouverture de droit. Je le maintiens **important** malgré l'impact limité, parce que c'est un piège latent et que le correctif est trivial et résout aussi le point mineur 2.5 : lire le Paiement via `->lire()` dans `page()` et empêcher `sanitiser()` de retomber sur `[]`.

**2.3 — Défaut Paiement dupliqué + lecture non uniforme (mineur).**
Vérifié : le défaut Paiement est recodé en dur dans `Reglages.php:37-38` **et** dans `ReglagesAdministration.php:25-28` (deux copies, risque de dérive si le défaut C-05 change). Et `page()` lit Accès/Envoi via `->lire()` mais Paiement via `get_option()` brut (`Reglages.php:192-194`).
**Avis : retenu, mineur.** `ReglagesAdministration` n'expose pas d'accesseur public de défaut ; la correction proposée par Claude (exposer un accesseur et le réutiliser) est saine.

**2.4 — Mention « À confirmer par Imagine » codée en dur sur les huit champs (mineur).**
`Reglages.php:223`, non pilotée par un état ouverte/tranchée. Vérifié dans `docs/decisions.md` et `docs/arbitrages-2026-11-22.md` : les huit règles sont encore ouvertes, donc la mention est exacte aujourd'hui.
**Avis : retenu, mineur, non urgent.** À traiter le jour où Imagine tranche un premier réglage.

**2.5 — Journal sans purge (mineur).**
Une option par événement, non autoloadée (`Reglages.php:121,125`) ; `options` croît sans borne ; affichage plafonné à 50 (`:133`). Assumé dans `notes.md`.
**Avis : retenu, mineur.** Codex confirme le constat (« la limite d'affichage à 50 ne supprime pas les anciennes entrées »). → arbitrage B.

### Vus par Codex seul

**2.6 — L'écran présente comme effectifs des réglages d'accès non raccordés (C10-01, important).**
`Reglages.php:148-160` : l'explication « L'autre choix autorise seulement l'équipe » accompagne un choix enregistrable, sans dire que ce choix reste sans effet sur le paywall actuel. Un administrateur peut enregistrer « Ouvert à l'équipe uniquement », voir un succès, et croire le comportement actif. La mention « À confirmer par Imagine » décrit une décision métier provisoire, pas une absence de raccordement.
**Avis : retenu, important.** Vérifié : le seul avertissement présent (`Reglages.php:197`, « Enregistrer ne lance ni paiement, ni email, ni envoi postal ») parle des effets de bord d'envoi, pas du fait que les réglages Accès/Paiement n'agissent pas encore sur le site. Le fait sous-jacent (non-raccordement) est acté par les deux relecteurs. Correction de Codex juste et peu coûteuse : préciser dans les sections Accès et Paiement que les valeurs sont conservées pour un branchement futur et ne modifient pas encore les accès/le paiement du site de démonstration. C'est un correctif d'écran, pas une nouvelle livraison du paywall.

**2.7 — Échec d'écriture du journal ignoré (C10-03, important par Codex).**
`Reglages.php:121` : le retour de `add_option()` n'est jamais contrôlé. Si l'option métier est enregistrée mais que l'insertion de l'événement échoue, le traitement se termine normalement ; la modification persiste sans trace et sans avertissement, et un ré-enregistrement de la même valeur ne répare rien (plus de changement détecté).
**Avis : retenu — Codex a vu ce que Claude a manqué.** Constat statique exact. Le brief exige « chaque modification est journalisée ». Probabilité faible (échec d'écriture DB), mais l'exigence est explicite et il n'existe aucun signalement. Je le maintiens **important** sur le principe, en allégeant le correctif attendu : contrôler le retour de `add_option()` et, en cas d'échec, signaler à l'administrateur (ne pas présenter l'enregistrement comme pleinement réussi). Le mécanisme de reprise/conservation proposé par Codex est plus lourd → voir arbitrage C.

**2.8 — Le test de forme n'isole pas la clé surnuméraire (C10-02, mineur).**
Vérifié `c10-verifier.py:162-165` : les formes testées pour Accès/Paiement sont une chaîne, `{}` et `{'extra':'invalide'}`. Cette dernière manque aussi toutes les clés obligatoires : elle prouve le refus d'un tableau incomplet, pas le refus d'une clé **supplémentaire** quand toutes les clés obligatoires sont présentes.
**Avis : retenu, mineur.** Le code refuse bien ce cas (`clesExactes()` compare le `count`, `Reglages.php:96`), mais le test ne le prouve pas. Correction de Codex juste : partir d'un domaine valide, ajouter une seule clé inconnue, vérifier refus + conservation exacte + absence d'événement ; tester séparément le retrait d'une seule clé obligatoire. À noter aussi (Codex) : aucun test n'associe un domaine invalide à un autre domaine réellement modifié dans la même soumission.

**2.9 — Façade non conforme PSR-12 (C10-04, mineur).**
`Reglages.php:45` (et appels multilignes similaires) : arguments répartis sur plusieurs lignes avec plusieurs arguments sur la première et la parenthèse fermante après le dernier argument — contraire à la règle PSR-12 des listes multilignes.
**Avis : retenu, mineur.** Les preuves C10 ne comportent pas de résultat `composer lint`. À reformater, puis lancer le lint du projet et joindre son résultat.

## 3. Désaccords

**Un seul désaccord réel : le verdict.** Claude conclut « À corriger » **avec un point bloquant** (absence de tests PHPUnit) ; Codex conclut « À corriger » **sans aucun bloquant**.

**Je tranche en faveur de Claude : le point 2.1 est bloquant.** Motif : le livrable n°1 du brief exige explicitement « Le code **et ses tests** (droits, nonce, valeurs invalides, journal) » ; la doctrine §4 impose une logique métier testable hors WordPress et §6 adosse la clôture à `composer test` au vert. Or `composer test` ne teste rien de C-10 et la logique pure (clés exactes, refus, dé-duplication du journal) est trivialement testable. Codex n'a pas pesé cet écart ; son « aucun bloquant » tient à ce qu'il n'a pas examiné la couverture PHPUnit de la façade. Sur le reste (importants/mineurs), les deux rapports sont complémentaires, pas contradictoires.

**Sur les tests exécutés (fait honnête à consigner) :** Codex a lancé `python -B -m unittest discover -s wp/tests/demo -p test_c10_scope.py` → 4 tests OK (gardes de déploiement, pas la logique WordPress). Ni Claude ni Codex n'ont pu lancer PHPUnit : `docker` absent du PATH côté Claude, binaire `php` introuvable côté Codex. Les 13 contrôles runtime, 79 HTTP et 30 non-régression C08 sont des **preuves livrées, lues mais non rejouées** (elles visent le site de démonstration, hors des droits de relecture). Aucune des deux relectures ne vaut donc confirmation indépendante des tests contre le site.

## 4. Instructions pour Hermès (numérotées)

1. **(Bloquant)** Créer `tests/Administration/ReglagesTest.php` et déclarer la suite dans `phpunit.xml`. Couvrir au minimum : clés exactes acceptées/refusées pour Accès et Paiement ; valeur hors liste refusée avec conservation de l'ancienne ; journal écrit **une fois** par option modifiée **après persistance**, rien sur un refus ni sur un no-op ; `apercuCsv()` reflète le format relu. Lancer `composer test` dans l'environnement autorisé et joindre la sortie. (réf. 2.1 ; doctrine §4/§6)
2. **(Important)** Dans `page()`, lire le Paiement via `(new Paiement())->lire()` comme Accès et Envoi (`Reglages.php:192-194`). (réf. 2.2, 2.3)
3. **(Important)** Empêcher la persistance d'un `[]` : faire que `ReglagesAdministration::sanitiser()` retombe sur le défaut déclaré plutôt que sur `get_option(self::OPTION, [])` quand l'option n'existe pas encore (`ReglagesAdministration.php:56`). Ajouter un test du tout premier enregistrement avec clés exactes mais valeur de type invalide. (réf. 2.2)
4. **(Important)** Ajouter dans les sections Accès et Paiement de l'écran une phrase indiquant que ces valeurs sont conservées pour un branchement futur et ne modifient pas encore les accès ni le paiement du site de démonstration. Ajouter une assertion sur ce texte. (réf. 2.6)
5. **(Important)** Contrôler le retour de `add_option()` du journal (`Reglages.php:121`) ; en cas d'échec, signaler à l'administrateur et ne pas présenter l'enregistrement comme pleinement réussi. Ajouter un test « écriture métier OK, écriture du journal KO ». (réf. 2.7 ; périmètre à arbitrer, voir C)
6. **(Mineur)** Isoler le test de clé surnuméraire (`c10-verifier.py:163`) : partir d'un domaine valide, ajouter une seule clé inconnue, vérifier refus + conservation exacte + absence d'événement ; tester séparément le retrait d'une seule clé obligatoire ; et ajouter un cas « domaine invalide + autre domaine modifié dans la même soumission ». (réf. 2.8)
7. **(Mineur)** Dédoublonner le défaut Paiement : exposer un accesseur de défaut sur `ReglagesAdministration` et le réutiliser dans `Reglages.php:37-38`. (réf. 2.3)
8. **(Mineur)** Reformater la façade selon PSR-12 (`Reglages.php:45` et appels multilignes), lancer `composer lint` et joindre le résultat. (réf. 2.9)
9. **(Mineur, non urgent)** Piloter la mention « À confirmer par Imagine » par un état ouverte/tranchée plutôt qu'en dur (`Reglages.php:223`), pour le jour où Imagine tranche un premier réglage. (réf. 2.4)
