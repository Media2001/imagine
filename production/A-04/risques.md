# A-04 — risques avant le vrai site (une page)

1. **Écart de pile, explicitement mesuré.** La fixture complète part de WP 7.0 / Woo 11.0.1 / Subscriptions 9.4.1 / Memberships 1.30.3, vers WP 7.0.9 / Woo 11.1.1 / mêmes premium. Un vrai WP 6.9.1 accepte Woo 11.0.1 mais refuse nativement Subscriptions 9.4.1 (minimum WP 7.0), sans contournement. Ni l'ancien Subscriptions, ni ses migrations historiques, ni la conservation de ses vrais moyens de paiement ne sont prouvés. Memberships est rejoué à version constante : ce n'est pas une montée historique de Memberships. Pas de preuve de migration de base complète 6.9.1 → 7.0 sur la pile commerciale entière.
2. **Migrations tierces.** Les API natives sont utilisées ; la queue Woo est drainée par ID et liste fermée, y compris les suites créées au bootstrap suivant. Les anciennes migrations WCS, les tâches failed/in-progress et tout traitement inconnu bloquent ; elles ne sont jamais « terminées » par changement aveugle de version. `bootstrap-only` pour le reste exige une trace d'audit nommant le composant, liée par SHA-256 à un fichier non vide concluant à l'absence de migration différée ; cela ne certifie pas la qualité de l'audit humain. Le balayage reste `(?!)`. Tout autre adaptateur au-delà des quatre premiers est refusé : une extension nécessitant un autre mécanisme est exclue du plan, jusqu'à un lot de support et qualification dédiés.
3. **Pas de rollback automatique.** DDL, changements d'options et migrations natives ne forment pas une transaction globale. Une interruption entre l'effet d'un callback et son acquittement peut entraîner son rejeu natif. Les anciens checkpoints ne sont pas recommencés. Sauvegarde récente base + fichiers, test de restauration séparé, opérateur disponible et maintien en 503 sont indispensables.
4. **Nettoyage volontairement exclu.** Aucun thème ni stockage classique/HPOS n'est changé. Les fichiers retirés des distributions restent présents, et les migrations natives peuvent supprimer leurs propres objets obsolètes : ce n'est pas un nettoyage A-05 général. Le risque de vieux fichiers, surcharges de thème et plugins non audités doit être levé lors de la répétition réelle.
5. **Gel externe et garde-fous.** Les verrous empêchent deux mises à jour de cet outil, y compris avec un autre état ou un enfant WP-CLI orphelin. Ils ne gèlent pas les écritures d'un autre déploiement/CLI/service. Le MU persistant interdit le HTTP dynamique après expiration de `.maintenance` ; mail, HTTP, paiements et queues sont bloqués dans le processus opérateur. Les appels réseau directs qu'un tiers ferait hors des transports WordPress ne sont pas un pare-feu système ; les fixtures, elles, sont réellement `network none`.
6. **GO et réception.** Le GO de production est borné au site/plan/délai mais reste une attestation locale, non une authentification cryptographique. La branche production n'a touché que des données fictives ; rien ici n'autorise le réel. Seul le verdict natif A-03 est admis : code 3 pour les changements uniquement attendus, code 0 pour l'identique, jamais de qualification alternative d'un code 2. Le serveur HTTP du banc journalise réellement en UTC et chaque nouvelle photo inclut son bilan borné `php_log` ; les anciennes photos sans ce bilan restent historiques. Les écritures HTTP natives de la fixture sont annulées et la séquence d'options restaurée : aucune promesse générale de HTTP sans écriture. Répétition sur staging Imagine vérifié et GO Ced nécessaires avant tout réel.
