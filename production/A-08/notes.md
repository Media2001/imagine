- Deux rendez-vous explicites plutôt qu'une automatisation dangereuse : après la photo avant pour préparer écriture/maintenance, après nettoyage pour préparer une réception HTTP privée sous compte SELECT. Sans eux, les exigences A03 et A04/A05 se contredisent matériellement. Aucun drapeau ne modifie un garde-fou : les outils natifs sont réellement invoqués et restent arbitres.
- Reprise limitée à la première étape non réussie. Une lecture interrompue recommence dans une sortie neuve ; les écritures reprennent l'état natif A04/A05. Les preuves réussies sont liées aux empreintes, les plans/settings/sauvegarde/outils restent identiques. La configuration SQL du site change seulement par l'opérateur aux rendez-vous ; les checkpoints natifs contrôlent leur propre configuration écriture.
- `--new-pass` refait audit, avant, vérifications de mise à jour, nettoyage, après, comparaison ; il conserve les checkpoints natifs, les photos et reçus du passage précédent. Un appel sans ce drapeau sur état terminé ne lance aucun outil.
- Échec natif de comparaison = arrêt. Le code 3 n'est pas converti en anomalie ; le code 2 n'est jamais requalifié. Le compteur attendu de la synthèse est uniquement le décompte des classes natives `attendu`, car le JSON natif n'expose pas ce compteur.
- Aucun raccord de configuration partagé : tests A08 en Python, exécutés dans le conteneur A08 ; PHPUnit/Composer et les suites acceptées restent inchangés. `preparer-image.ps1` a néanmoins été relancé comme demandé, avant tout PRET. Pas de revendication de rejeu global T01.

## Banc, qualification et limites

- PHP, WP-CLI, MariaDB et les extensions réelles de test tournent exclusivement dans le conteneur jetable A08 : label distinct, nom exact, réseau absent, aucun montage/port, capacités retirées et ownership contrôlé avant suppression. Aucune archive Imagine, aucun compte/donnée réelle, aucun site de staging ou de démonstration.
- Réutilisation du banc accepté A04/A05 : WordPress 7.0 au départ, ancien Woo public épinglé, mêmes ZIP Subscriptions/Memberships déjà autorisés. La pile commerciale épinglée exige WordPress 7.0 : aucune preuve de montée complète 6.9.1 → 7.0 ni de migrations historiques premium n'est ajoutée. Les marqueurs et sondes staging restent réellement contrôlés.
- Les archives publiques A04 manquaient dans l'arborescence Windows. Alternative effectuée : helper A04 inchangé importé sans bytecode, sortie redirigée vers `production/A-08/dependances/`, uniquement deux ZIP publics verrouillés, SHA-256 comparés au lock A04. Aucun téléchargement pendant les tests hors réseau.
- Comme dans la fixture A03 acceptée, HTTP exécute les écritures natives en rollback ; le banc rétablit explicitement après chaque réception la séquence synthétique `wp_options` et vérifie sa relecture. Ce geste de fixture ne fait pas partie du wrapper et ne prouve pas une absence de toute écriture HTTP sur un vrai site.
- Les préparations opérateur de la fixture retirent explicitement les maintenances pour le HTTP privé, conservent leurs octets hors web, puis rétablissent le MU de maintenance à l'identique pour le second passage. La garde staging demeure byte-for-byte intacte ; l'isolation réseau externe ne cesse jamais. Ce n'est pas une exposition ni une ouverture au public.
- A03 n'est pas un inventaire exhaustif des plugins/cron/tables. La disparition des déchets fictifs nommés est donc prouvée par inventaire séparé, sans altérer son verdict. Une comparaison identique ne suffit pas à elle seule à prouver le nettoyage.
- « Second passage sans changement » est qualifié au sens métier, pas comme absence absolue d'écriture : A04 rafraîchit `.maintenance` ; le bootstrap natif Subscriptions 9.4.1 réécrit à chaque `woocommerce_init` l'expiration `_transient_timeout_wcs_woocommerce_active_version`. Ce constat est lié au hash du fichier PHP tiers réel. Le cache de version lui-même, toutes les autres lignes d'options, tous les autres fichiers et toutes les autres tables restent identiques ; les empreintes brutes et les deux rafraîchissements restent visibles. Le comparateur A03 non modifié donne réellement zéro changement au second passage. Les premiers reçus qui exigeaient l'immobilité brute restent échoués/historiques : ils ne sont pas réétiquetés verts. Si l'exigence est interprétée comme zéro écriture technique absolue, elle n'est pas satisfaite sans modifier A04/Subscriptions, ce qui est hors périmètre et n'a pas été fait.
- Au scellement, un cache hôte `wp/tests/a05/__pycache__/test_clean.cpython-314.pyc`, daté de 20 h 27 min 55 s, est apparu hors des sources et du paquet testé. Son propriétaire n'est pas établi : il est laissé intact, jamais supprimé au nom d'A08. L'inventaire source ignore explicitement `__pycache__`, pas les fichiers source ; les empreintes de ce paquet historique sont conservées, sans prétendre que ce baseline ancien décrit les ajouts A09/A10 ultérieurs. Tous les orchestrateurs A08 hôtes ont tourné avec `-B` et les imports de banc désactivent le bytecode.
- Les durées excluent préparation de fixture, sauvegarde, attentes opérateur et restauration. Elles ne dimensionnent pas le site réel. L'intégrité d'une sauvegarde n'est pas une preuve de restaurabilité.
- La chaîne complète A08 est qualifiée sur copies fictives classiques et HPOS uniquement. A03 exige une copie vérifiée : pas de qualification de réception production. Les GO A04 et A05 sont distincts et simplement transmis ; aucun GO réel livré ni implicite.
